# Full-context screen-reading acceptance

The requested application automatically follows the participant's own Street Brawl match, shows four allied and four opposing heroes with observed current builds, tracks the local hero's ability investment, and uses that context when comparing actual offers. Visible-screen reading is authorized. The application observes the game; the human opens normal game panels and performs every game action.

The user's latest display preference is an essential view: emphasize the item to consider and keep enemy heroes/items visible. Own build and ability advice, allies, calculations, reroll evidence and configuration belong in closed details. This changes presentation, not acquisition or the contextual calculations. A short warning beside conditional base-effects guidance remains visible even when every detail is closed.

Source inspection identifies implementable surfaces. It does not establish that the recognizer reads them accurately in a match. The user was no longer in a match during this audit; no scoreboard, inventory, ability, or recommendation accuracy was certified from live gameplay.

The expanded hero label is especially small and low opacity in the current styles. OCR-only roster acquisition is therefore insufficient as an accuracy claim; portraits can supplement it only when template/layout confidence is adequate. The highlighted top-bar ring is shared by local, spectator-target and other highlighted states, so it is not unique local-player evidence. The top-bar player layout has a separate `SpectatorImage` glyph, made visible by the `SpectatorTarget` class; an unread or unchecked spectator region cannot prove its absence. A unique active Steam display-name match may corroborate a separately observed participant HUD hero, but it is a display-name association rather than SteamID proof.

No enemy-specific rank hide rule was found in the inspected top-bar/icon CSS. This does not prove that enemy rank data is rendered at runtime. Collapsed, pregame-hidden, unreadable or unpopulated indicators remain unknown. The screen route cannot observe private enemy offers, unshown modifier details, panels the human has not displayed, or a future random reroll result.

The current native recognizer emits positive or unknown item-cell readings and keeps inventory regions partial. The reducer supports explicit empty cells and complete replacement, but that contract is not proof that the production reader can presently confirm every removal or upgraded variant. Enemy rows therefore show observed items with age and coverage, rather than a certified complete current loadout. A later normal-game test must verify the actual owned-grid geometry and replacement behavior.

## Implementation checks

- [ ] Acquisition scans the ordinary HUD and expanded scoreboard as well as the draft. A title-only scan cannot silently become the only outside-draft path. No keyboard input opens a panel for the human.
- [ ] Native context reports recognized, unknown, hidden and empty cells separately. It preserves the capture bounds, real capture time, frame ID, reader epoch, game-window session and per-field method/confidence. A process/window session is explicitly not a game match ID.
- [ ] Relative allied/opposing assignment is accepted only from a recognized participant layout. Spectator/replay layouts never receive participant team semantics by default.
- [ ] Local hero/seat ownership is observed independently of portrait brightness, roster order, a unique hero name, or a guessed player name. Deathcam/spectating/replay cannot replace own hero/build/AP/ranks.
- [ ] A complete roster requires eight distinct visible player panels and unambiguous side assignment. Partial visibility retains partial coverage. Duplicate hero names cannot collapse two seats.
- [ ] A complete inventory requires a fully visible owned grid, all applicable groups, known bounds/count and an explicit result for each cell. Recognizing three icons is not a complete three-item inventory. Unknown cells are retained; a cropped row is not an empty row.
- [ ] Accepted complete inventory snapshots replace old slots and remove absent items. Partial scans update only what was observed and cannot infer a sale, replacement or upgrade. Instance multiplicity and locked-group membership survive; no fixed 12-item cap truncates the result.
- [ ] Closing the scoreboard does not refresh its fields. The interface says when builds were last seen; old enemy items may provide qualified positive context but do not establish current absence, team coverage gaps or unchanged full inventories.
- [ ] When participant ownership or build freshness blocks an otherwise readable draft, the essential view identifies that specific dependency and tells the human to show the normal scoreboard. A generic confirming state cannot hide the need for a fresh visible panel. Repeated same-hero HUD frames do not silently renew an expired ownership proof.
- [ ] Actual ability rank, unlock state, unspent AP and observation coverage are independent. Rank zero and locked are distinct. Three readable bars do not automatically prove unlock state. Budget zero requires an actual zero reading.
- [ ] New game-window session, explicit new-match ID, match-end→new pregame, incompatible roster identity, or incompatible round/score regression retires dependent context. A same-process new match must not inherit old items. Ambiguous boundaries lower coverage until compatible observations arrive.
- [ ] Draft advice is keyed to the reader/match epoch, offer generation, local identity, team/roster, inventory and ability revisions, catalogue and evaluator. Any relevant accepted context change clears the old result before recomputing. A late result cannot restore it.
- [ ] Offers expire independently of acquisition cadence. Tentative readings stop claiming an open draft after a short bounded interval. Normal combat is presented as a useful build/roster view, not an endless confirmation task.
- [ ] One native request at a time, low scan rates, below-normal worker priority, bounded CPU work and no backlog remain enforced when full-context image matching is added. Own HUD reads have a reserved work budget, and item/player traversal rotates or otherwise guarantees progress; exhausting the budget on the same early cells must not starve the local hero or later teammates/opponents forever. Performance claims measure the whole packaged application; no synthetic FPS claim is made.

## Recommendation completeness

Context-aware item guidance applies every identified main/bonus component to the observed local build, uses pinned Street Brawl mechanics, and explains how the observed team or opponent situation affects the choice. A generic item utility score with a hero label attached does not meet this requirement.

The current production fallback is a separate **Base item to consider** comparison, presented in the essential view with **Main item only · bonuses or special effects unread**. It requires reliable identities for all three main items and usable actual participant context, excludes every bonus and special modifier consistently, and withholds a highlighted result for an undecoded owned-item repeat. Its position is separate from the firm full-card preference. This is conditional main-item guidance; it does not certify full-bundle value or an optimal match recommendation. Positive visual evidence for plain-card/modifier/bonus coverage and actual reroll replacement semantics remain unresolved requirements.

- [ ] Upgrade paths, owned-component replacement, overlapping/non-stacking effects and diminishing returns are evaluated explicitly where they matter. Unknown special modifiers do not become base effects. Missing effects lower certainty or withhold the affected preference.
- [ ] Rank-sensitive effects use actual observed local investment. Own weapon/spirit/active synergies refer to observed items; enemy healing/mitigation/control answers refer to actual observed items or clearly labelled hero-mechanics potential.
- [ ] Missing teammate items cannot be called a team utility gap. Existing observed coverage can reduce redundant utility only under a documented stacking rule. Every explanation identifies the contextual fact and its limitation.
- [ ] With identical offers, meaningful changes to own hero/build, ability investment, enemy sustain/damage or allied utility change relevant components or explanations. Tests inspect mechanics-specific differences rather than merely asserting that some numeric score changed.
- [ ] The interface identifies a situational recommendation and evidence limits. It does not call an arbitrary weighted score an optimal pick, calibrated confidence, win probability or measured policy improvement.
- [ ] **Next ability upgrade remains available in match details.** It uses actual ranks/unlocks and pinned next-tier effects. An upgrade-now instruction also requires fresh observed unspent AP and a source-verified next-tier price, or fresh observed affordability for that tier. The pip XML exposes a runtime price label and three tiers; it does not itself establish a hard-coded 1/2/5 price schedule. Prices must belong to the next unpaid tier, rather than another row. The upward flow places tier 1 below tier 3; bought markers form a consistent paid prefix. If legality is unread or the local budget/rank ages out, a clearly labelled conditional next priority may be shown; its missing dependency remains visible beside that priority.
- [ ] **Reroll evidence remains available in details.** Observed count, legal availability, remaining time and a replacement-model status are separate. Zero means unavailable only after an actual zero reading. A named current pick is never treated as a retained fallback after reroll.
- [ ] Reroll estimates use a documented conditional draw/replacement model and future pick/round value; static weights are labelled assumptions until their actual draw semantics are validated. No precise chance, reroll-now directive or extra arbitrary scarcity penalty is invented from selected-purchase statistics. Model-missing status explains the specific missing dependency.

## Required integration and game checks

| Check | Concrete expectation |
| --- | --- |
| Unattended loop | With auto-start enabled, advance timers only through HUD→scoreboard→draft→combat and ten minutes of idle play. No manual polling, backlog, stale choice or indefinite confirming state |
| Actual schema boundary | Native context JSON reaches the production adapter/store/UI and scorer with per-cell status/provenance. Fixture-only parser branches do not count as native tracking |
| Spectate transition | Own build/AP/ranks observed, then another player's HUD appears with a spectating/deathcam cue. Own state is not replaced and own upgrade-now advice clears |
| Partial→full→partial grid | Full `[A,B,C]`, unread/cropped `[B,D]`, then full `[B,D]`. Partial cannot remove A/C; the next complete view replaces the grid; unknown slots remain unknown |
| Identity/reordering | Two equal hero labels, reversed allied flow, reordered panels and a new hero in an old position. No seat collapse or build transfer |
| Rank/budget ambiguity | Hidden pips, cost labels, cooldown digits and team AP totals never become local ranks/AP. Explicit zero and affordable-next-tier views remain distinguishable |
| Context changes under same offers | Own upgrade, local item replacement or enemy counter item while a draft is unchanged. Previous advice disappears atomically and the new reasoning uses the accepted revision |
| Essential view | Close every detail. Current item guidance and enemy heroes/items remain prominent; the base-effects caveat and unread/stale enemy coverage stay visible. Background own/allied observations still influence the comparison |
| Same-process new match | Post-match→new roster/pregame without restarting Deadlock. Old inventories, ranks, offers and advice cannot reappear from delayed captures |
| Real ordinary game | Human shows the scoreboard/upgrade view during normal play. Compare all eight heroes, owned grids, local identity/AP/ranks, picks/rerolls and closure against the visible game; report misses per surface/resolution |
| Resource comparison | Compare paused versus enabled whole-app CPU/memory and game frame times during the same scenario. Current helper-only fixture timings establish neither reading accuracy nor absence of stutter |
| Budget fairness | Use the full roster and a long item grid so early matches consume most available work. Repeated scans still acquire the local HUD and later players, rather than repeating only the first cells |

Automated contract checks and normal-game accuracy checks are different evidence. Before describing the full intended product as complete, every promised feature must either be demonstrated through the production path or explicitly identified as an implemented but unverified capability with the next practical test. Unknown dependencies remain visible; they are not silently omitted.
